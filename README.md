# Генерация карточек товаров с помощью LLM

Рабочий репозиторий проекта генерации карточек товаров.

# Отчёт по проекту

## Финальный конфиг
- модель: `Qwen/Qwen2.5-1.5B-Instruct`
- dtype: `float16`
- параметры запуска vLLM: `nohup vllm serve Qwen/Qwen2.5-1.5B-Instruct --dtype half --max-model-len 4096 \
  --gpu-memory-utilization 0.9 --enforce-eager --enable-prefix-caching --port 8000 > vllm.log 2>&1 &`
- параметры генерации: `temperature=0.5`, `top_p=0.9`, `top_k` без ограничения, `repetition_penalty=1.1`, `max_tokens=250`;
- concurrency: `48`;
- стратегия длинного входа: удаление дубликатов/похожих отзывов, затем отбор из оставшихся с чередованием длинных и коротких до лимита 1500 токенов;
- при браке формата выполняется повторная генерация с указанием модели причины ошибок;
- максимальное число попыток генерации: 2.

Анализ кэшированных результатов показал, что ошибки, устраняемые повторным запросом, устраняются со второй попытки; если вторая попытка не помогает, то и третья не дает ощутимого выигрыша.

- корректность JSON;

## Сравнение с моделью через API
Для сравнения использовались 20 товаров из `dev.jsonl` с одинаковыми промптом, параметрами генерации и обработкой длинного входа. 
Локальная модель запускалась с `concurrency=1`, через OpenRouter использовалась `apodex/apodex-1.1-mini:free`.

| Метрика | Qwen | OpenRouter |
|---|---:|---:|
| Доля валидных | 85.0% | 100.0% |
| Входных токенов на карточку | 1844.9 | 1276.4 |
| Выходных токенов на карточку | 277.9 | 219.8 |
| Средняя latency, с | 5.51 | 2.20 |
| Среднее число попыток | 1.45 | 1.15 |
| Стоимость 1000 карточек | 9.22₽ | 38.72₽ |

В клиенте предусмотрены повторы с экспоненциальной задержкой для `429`, `5xx`, таймаутов и ошибок соединения. Ошибка `400` обрабатывается без повтора. Во время прогона ошибок API не возникло.

**Итог**: доля валидных карточек оказалась выше при использовании API, однако использование локальной модели обходится дешевле. Сравнение по latency условное из-за сетевых задержек API.

## Длинный вход
К `reviews` карточек, превышающих лимит 1500 входных токенов, последовательно применялись:
- удаление точных дубликатов в reviews;
- удаление похожих reviews (`similarity` >= 0.9);
- отбор reviews до лимита 1500 токенов.

Всего удалено 462 дубликата и 91 похожий отзыв.

На карточках, превышающих лимит после удаления дубликатов, сравнивались две стратегии финального отбора:
| Стратегия | Среднее число выбранных отзывов | Среднее число входных токенов | Максимум токенов | Среднее время обработки |
|---|---:|---:|---:|---:|
| длинные + короткие отзывы | 29.0 | 1195.0 | 1499 | 69.5 мс |
| последовательная обрезка | 26.3 | 1195.5 | 1495 | 61.8 мс |

**Итог:** выбрана стратегия чередования длинных и коротких отзывов, поскольку при сопоставимом размере входа она сохраняет в среднем больше отзывов. 

На полном `benchmark.jsonl` после предварительной обработки максимальный размер входа составил 1500 токенов, средний - 1188.88 токена.

## Оптимизации
Сравнивались FP16 и INT4 на одной и той же выборке из 80 товаров при `concurrency=48` и включенном `prefix caching`.

| Точность | throughput, карточек/с | avg. latency, с | valid rate | avg. attempts |
|---|---:|---:|---:|---:|
| **FP16** | **1.987** | **19.739** | **93.8%** | **1.238** |
| INT4 | 0.485 | 79.152 | 85.0% | 1.400 |

INT4 не дал выигрыша в производительности, а также привел к росту среднего числа попыток генерации и количества ошибок формата.

**Итог:** выбран FP16.

## Стоимость и решение
Стоимость локальной модели по полному `benchmark.jsonl`:

`(153.1 / 3600 * 65) / 300 * 1000 = 9.22₽`

Стоимость API по 20 товарам из `dev.jsonl`:

`(25528 * 20 + 4396 * 60) / 1000000 / 20 * 1000 = 38.72₽`

При плановом объеме 50000 карточек стоимость локальной обработки составит около 461₽ при оплате только времени генерации, API - около 1936₽.

Стоимость непрерывной аренды ВМ на 30 дней: `65 * 24 * 30 = 46800₽`

Точка равенства стоимости API и постоянно арендованной ВМ: `46800 / 38.716 * 1000 ≈ 1.21 млн карточек в месяц`. При меньшем объеме API выгоднее.

Если ВМ оплачивается только во время обработки, локальная модель дешевле API при любом объеме по полученным замерам.

**Итог:** выбран локальный vLLM. Он удовлетворяет требованиям по валидности формата, скорости, длине входа и стоимости.
